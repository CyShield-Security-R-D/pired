## ADR draft 2.5 — A matched-compute arm runs the candidate without delegation at the candidate's token budget, beside the gate

**Status:** draft · 2026-09-26 · Phase 2 item 2.5 of `docs/delegation-v6-plan.md` · design in
`docs/delegation-v6-phase2-design.md` §2.5, amended as recorded under *Decision* · follows ADR-026,
ADR-030, ADR-031, ADR-033

### Context

The v5 trial compared a delegating candidate with a baseline that spent less. From
`research/12-delegation-trial-2026-09.md`:
- On the gating Luna grid (v5c) the candidate's pass-mean true positives went from 2.00 to 2.33, and
  its tokens from 27.0M to 43.8M (+62%).
- Whether that gain is delegation or spend cannot be read from those two arms. Across agent systems,
  spend explained about 80% of performance variance in the multi-agent study research/12 cites, and
  the controlled 260-configuration study it cites compared designs *at matched tokens*. A
  comparison that does not match compute partly measures "more tokens against fewer".
- The trial's own observational data does not settle it either. True positives per run were roughly
  flat across token buckets (Luna baseline 0.44–0.67 from under 2M to 25M tokens; GLM baseline 1.40
  at 2–5M against 1.27 at 5–10M), but tokens there are an outcome, not a treatment. Only an arm whose
  budget is set from outside answers it.
- A single Luna session cannot simply be given more tokens: about 40% of Luna runs end within 5
  minutes, and 32 of 41 baseline runs end by offering to continue. Unattended, the run ends, and a
  larger budget goes unspent.

So the question the arm answers is: does a single agent, given the tokens the candidate spent,
find what the candidate found?

### Decision

- **The arm is the candidate snapshot with delegation off.** Its scope states `maxAgents 0`, and it
  loads the same pinned pi-subagents tree as the candidate, so it is the candidate as an operator
  would switch delegation off. The baseline snapshot was rejected (see *Rejected*).
  `--matched-snapshot` overrides the snapshot for exploratory use; the preflight stages and pins
  it, and the grid becomes exploratory unless it is byte-identical to the candidate.
- **Sessions in fresh cells** (`--matched`: k = 3 by default, at most 8; kMax = 2k by default, at
  most 16; floor = 5% of B). Each session gets its own cell, staged snapshot and ledger, as any run
  does.
- **Budget modes, pinned in the manifest as `matched` with k, kMax and the floor:**
  - **`follow`** (default). The arm runs after its pair, and its total budget B is that pair's
    candidate run's tokens, the metric the gate reads (metered, plus the retry estimate under
    `--retry`).
  - **`fixed`**. B is a pre-registered per-target number (`budget.<target>=<tokens>`), for the
    concurrent runner of item 2.2. Until that lands it runs in the same slot as `follow`.
  - A resume restores the policy from the manifest and `resumeMismatches` refuses one that differs.
    A manifest without `matched` loads unchanged and runs no matched arm.
- **Splitting B: rollover, then extra sessions** (review). `nextSessionStep` plans every session
  from the ones already run:
  - **Rollover.** Session i ≤ k gets floor((B − spent) / (k − i + 1)), where spent is the valid
    sessions' tokens before it. A session that stops early leaves its share to the rest.
  - **Extra sessions.** After the first k, while at least the floor (5% of B) is left and fewer
    than kMax sessions have run, one more session runs with all of what is left.
  - **Re-runs.** A session re-run after an infrastructure failure keeps its index's original
    ceiling, so a drop does not move the split.
  - The arm is complete when the plan says so, and `scoreUnion` asks the same function.
- **A token ceiling in the entry.** `tokenCeiling` in the cell config. A session listener meters
  every assistant reply and completed compaction that reports tokens.
  - **A reply that reaches the ceiling** is metered at its `message_end`, and the abort waits for
    that turn's `turn_end` (review). The reply's tool calls run first, so a `record` in it lands in
    the ledger; running a tool costs no tokens. An abort at `message_end`, the first version,
    turned every call in the crossing reply into "Operation aborted" and lost its findings.
  - **A compaction that reaches it** aborts at once, since its `compaction_end` is between requests.
  - **A compaction that starts after it** is aborted at its `compaction_start` with pi's
    `abortCompaction`. pi checks that signal before resolving the summary's auth, so no summary
    request is sent. This matters because pi runs a threshold compaction before the next request,
    and an overflow one in the turn's finish (review).
  - pi calls the listener while the agent loop awaits its own listeners, so the abort lands before
    the next request, and every request sent is metered. The reviewer confirmed from pi 0.87.1's
    source that the run then ends in print mode with exit 0, on the empty "This operation was
    aborted" setup reply with zero usage, with no retry and no post-run compaction.
  - The accounting drops that reply, as it already did for a worker aborted between requests, and it
    counts neither as a request nor as a missing response ID. The accounting accepts a compaction
    the ceiling aborted, and an in-flight abort still fails the session because its spend is
    unknown.
  - The entry prints `benchmark_token_ceiling` as the transcript's last line. The ADR-030
    classifier reads a cut session as `budget` (token ceiling).
- **The ceiling is verified, not trusted** (review).
  - The transcript's metered requests must sum to the line's `metered` and to the accounting's
    parent total.
  - They must first reach the ceiling at the line's `reachedAtRequest`, with nothing metered after
    it. Only a compaction the ceiling aborted may follow, and none may come before it.
  - Any mismatch makes the session invalid for harness integrity.
  - The preflight runs a sealed faux-model ceiling probe (zero real tokens). Its one scripted reply
    records an element and crosses a one-token ceiling. The probe requires three things: the
    record is in the ledger, the model was asked once, and the accounting accepts the cut with the
    ceiling verified and the stop read as budget.
- **When it runs.** After both arms of a pair are valid at the same attempt, never between them, so
  the pair's own two arms keep the timing they had before this arm existed. A pair that is re-run
  takes its matched sessions with it; under `follow` its new candidate run sets a new budget.
- **Failure and retry.** A failed session is re-run on its own, by the rule a pair is re-run by
  (`nextPairAction` with that session as its only arm), with the breaker's cooldown and caps.
  - Every launched session feeds the breaker, or fail-fast, like any run.
  - A session invalid for a non-infrastructure reason, or abandoned at the attempt ceiling, ends
    the arm for that pair. No further session is launched, live or on resume, since the union can
    no longer be valid (review). Such a failure does not trip an official grid's breaker at once,
    as a pair arm's does, because it leaves the gate's decision open.
  - A stop a matched session's failure caused does not by itself withhold the gate's approval. A
    bookkeeping write that fails during a matched session does, as any harness-integrity failure
    does (review).
  - A resume keeps each session at its own highest attempt, and runs a kept pair's arm on from the
    sessions it already has.
  - A session that launched a worker is invalid: delegation was not off.
- **The union.** The arm's findings are the union of its sessions' ledgers, each read as the
  pinned adapter reads a run's ledger, deduplicated by file and line with the pinned scorer's
  `dedupe` (as `eval/compounding-union.ts` accumulates sessions), and graded once with the pinned
  scorer. That is the arm's official number. Its tokens are the sum over the sessions. It is valid
  only when the session plan is complete and every session in it is valid.
- **Records.** Each session is a run in `runs.jsonl` and `run.json`, with `arm: "matched"`,
  `matchedSession {index, k, kMax, sessionAttempt, budget, ceiling, spentBefore, budgetSource,
  candidateCellId}` and `tokenCeiling`. `summary.json` gains a `matched` block: every pair's union,
  with the cells of its sessions, its budget and its score file.
- **Comparisons.** `compareMatchedRuns` still decides baseline vs candidate, and nothing about it
  changes. Two comparisons are added beside it and approve nothing:
  - matched vs candidate: delta = candidate − matched. This is the question the arm exists for.
  - matched vs baseline: delta = matched − baseline, what the extra tokens alone bought.

  Their `decision` field is dropped and their arm summaries are labelled by arm.
- **Realised budget ratio.** Matched tokens / candidate tokens per pair, and the median. The median
  is used because on Luna pooled token ratios swung from 0.51 to 2.86 between grids on single long
  runs, against median pair ratios of 0.62 to 1.36 (research/12).
- **Readers.**
  - `eval/paired.ts --arms matched,candidate` pairs any two arms, and its default is unchanged.
  - `eval/rescore.ts` folds each union's named sessions into one row, and checks its mirror against
    the union's official number. The union rows get their own control line and stay out of the run
    totals.
  - `eval/cost-breakdown.ts` counts sessions apart and never pairs them.
- **Pinned.** The new module `eval/delegation-compare-matched.ts` is in `HARNESS_FILES`.

### Fairness

- **Follow mode matches compute per pair, and adds time drift within the pair.** The arm runs after
  the pair's two arms finish, so it meets a later provider window than the candidate it is compared
  with, later by up to both arms' run time. This is the price of taking B from a measured run. Fixed
  mode removes the wait, but matches compute only in expectation, which is why the realised ratio
  is always reported.
- **A ceiling is where a session stops, not exactly what it spends.** A session stops after the
  reply that crosses its ceiling, so the overshoot is at most one request. Every request's
  `totalTokens` includes its cache reads, so that request is the whole context plus its output.
  - The crossing reply's tools still run, which spends nothing.
  - A compaction that would start after the crossing is aborted before its request, so it adds
    nothing.
  - The overshoot counts towards the arm's tokens and raises the realised ratio slightly above 1
    when every session runs to its ceiling.
- **Rollover, so that early stops do not starve the arm** (review).
  - About 40% of Luna runs end within 5 minutes (research/12). A fixed split of B / k would leave
    those sessions' shares unspent, and the arm below the candidate's compute. That would bias the
    comparison towards the candidate, for a reason that is not the single agent's ability.
  - Rolling each session's unspent budget into the next, and then running extra sessions on what
    is left, spends B unless the model stops early every time, kMax times over.
  - The costs:
    - more sessions, so more cold starts (see *k sessions are not one long session*);
    - the number of draws the union takes now varies by pair, between k and kMax;
    - the floor, 5% of B, is a choice: below it a fresh session would spend most of its budget
      re-reading the target.
  - A realised ratio well below 1 now means the model stopped early in kMax sessions in a row. That
    is a statement about the single agent, and the per-pair ratio shows it.
- **The crossing reply keeps its work** (review). Its tools run before the abort. A `record` there
  is kept, the same as a record in any other reply. Discarding it would have charged the arm for
  the reply's tokens and denied it the reply's findings.
- **The ceiling meters metered tokens; B includes the retry estimate.** Under `--retry`, B is the
  candidate's metered tokens plus the estimate for its unmetered failed attempts. The entry cannot
  see estimates, so the arm's sessions are held to metered tokens. Its own estimate is added
  afterwards to its gate-metric total, and the ratio compares like with like.
- **The union raises claims as well as true positives.**
  - A union of k draws finds more for any stochastic process. That was the artifact
    `compounding-union.ts` was written to catch, and here it is the point: the arm spends the budget
    as k draws.
  - Deduplication is by file and line only, so two sessions citing one issue at different lines
    count as two claims.
  - Extra sessions add draws, and so add claims too.
  - Compare pooled precision after deduplication, not true positives alone. research/12 found the
    candidate's precision falling from 0.103 to 0.061 on Luna v5c; a union can fall the same way
    without a worker in sight.
- **k sessions are not one long session.**
  - Each session starts cold and spends part of its budget re-reading and re-mapping what another
    session already read. One long session would carry that context instead, and compact it.
  - The arm therefore buys breadth (independent draws) rather than depth, which is the shape the
    candidate's workers also buy. A result where matched ≈ candidate says delegation added nothing
    beyond independent draws at that spend. It does not say a single long session would do as well.
  - k is pinned per grid, so this choice cannot drift within one.
- **The arm pays for the product's own delegation-off behaviour.** It loads pi-subagents at cap 0.
  pired since ADR-029 keeps the loader out of such a session, but a snapshot cut before that could
  still offer it. A model that tries to delegate is refused and pays for the attempt, as an operator
  running that snapshot with delegation off would. The attempts are counted in `subagentCalls`, and
  a worker actually launched invalidates the session.
- **Same model, effort, settings, seal, timeout and scorer.** Each session is bounded by the same
  per-arm time limit, and its ceiling usually ends it first. The union is graded by the same pinned
  scorer against the same truth.

### Consequences

- **Resumes across this change are refused.** The entry, lib, stop classifier and runner changed
  and a module was added to `HARNESS_FILES`, so `harnessSha256` differs. A grid started before this
  is resumed from a worktree at its own commit.
- **Without `--matched` nothing changes.** Manifests, `runs.jsonl`, cells, `progress.json` and
  `summary.json` keep their shapes. The existing tests pass unchanged, including the ones pinning
  the extractors' option-off output.
- **Cost.** By construction the arm spends about what the candidate spends. On v5c Luna's pass means
  (27.0M baseline, 43.8M candidate) that makes a pass cost about (27.0 + 2 × 43.8) / (27.0 + 43.8)
  ≈ 1.6× what it did. This is arithmetic on the measured means, not a measurement.
- **Time and the OAuth horizon.** Each pair now holds up to 2 + kMax runs. For the official grid (5
  targets, 3 passes, concurrency 2, 2 h per run, k = 3, kMax = 6):
  - Without a breaker, the worst case the OAuth check sizes grows from 36 h to 144 h.
  - With the default breaker it grows from 144.9 h to 576.9 h (360.9 h even at kMax = 3). That is
    past the 168 h cap the check would otherwise use without saying so.
  - So `--matched` with `--breaker` is refused unless `--auth-horizon-hours` states the bound
    (review).
  - The ceilings normally end sessions long before their time limit.
- **The preflight gains a ceiling probe** for a grid that runs the arm. It is scripted, sealed and
  spends no tokens.
- **Luna's early stops will show as ratios below 1.** Under ADR-030 the sessions' stop outcomes
  (`budget` vs `offered-to-continue`) are counted per arm under `stops.runs.matched`, which says
  whether the arm ran out of budget or chose to stop.
- **Not validated against a live model.** This change made no model or provider call.
  - The abort timing rests on pi 0.87.1's listener order and its `turn_end` placement after the
    turn's tool results (pi-agent-core `agent-loop.js`). An independent review confirmed that
    reading from pi's source.
  - The unit tests use a fake session, and the preflight's faux-model probe exercises the real pi
    and pired path before any grid starts.
  - The first pilot should still confirm on a real transcript that a cut session ends on the empty
    setup reply and never on an `aborted` one.

### Rejected

- **Running the baseline snapshot k times** (the design's first draft). Matched vs candidate would
  then differ in every product change between the snapshots, not only in delegation, and a
  difference could not be assigned to either.
- **Running the matched arm between the pair's two arms.** In a candidate-first pair it would widen
  the gap between the two arms the gate compares, changing the gate's own conditions.
- **One session at the full budget B.** Luna ends most runs on its own by offering to continue, so
  the budget would go unspent. It would also compare a deeper single context with the candidate's
  breadth, so it answers a different question.
- **A ceiling that aborts mid-request.** An aborted in-flight request reports no usage, so the arm
  would spend tokens the accounting cannot count, on the arm whose spend is the point.
- **Aborting at the crossing reply's `message_end`** (the first version). It kept every request
  metered, but turned the reply's tool calls into aborted calls and lost its findings.
- **A fixed split of B / k with no rollover** (the first version). Every Luna session that stopped
  early left its share unspent, and the comparison leaned towards the candidate.
- **Trusting the entry's ceiling line.** A wrong line would have passed silently. The transcript and
  the accounting now have to agree with it.
- **Scoring the union as the sum of the sessions' true positives.** One issue found by two sessions
  would count twice. The union is deduplicated and graded once, as the pinned scorer grades a run.
- **Letting a matched-session failure trip an official grid at once, as a pair arm's does.** That
  rule exists because such a failure fixes the gate's decision. A matched session's does not.
