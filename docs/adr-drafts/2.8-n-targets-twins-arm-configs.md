# ADR draft (2.8) — A grid takes any number of targets, runs patched twins beside the gate, configures each arm's scope, and is official only as a pinned corpus and grid kind

**Status:** draft · 2026-09-26 · Phase 2 item 2.8 of `docs/delegation-v6-plan.md` · follows ADR-026,
ADR-031, ADR-032, ADR-033 and ADR-034 · built on branch `p2/targets` (from `p3/candidate-v5`
ee5c9c8); no model calls, no probe or benchmark runs

### Context

- **The harness took exactly five targets.** `loadTargets` refused any manifest that did not
  resolve five, and "official" was the five v5 research ids, hard-coded in the lib
  (`OFFICIAL_TARGET_IDS`) beside the manifest and truth hashes hard-coded in the runner.
- **The v6 corpus is twelve targets plus a patched twin each.** The fresh corpus
  (`eval/corpus/fresh/` on `p4/fresh-corpus`) lists the twelve in `manifest.json` and their twins
  in a separate `twins.json`. A twin is its target's fix-commit tree; its answer key is an empty
  list, and its `fixed_regions` (72 across the twelve) are where a claim re-flags the fixed code.
  Each twin carries its target's advisory as `id` and its target's name as `twin_of`.
- **The trial runs in two stages** (`docs/delegation-v6-preregistration.md`, a draft): stage 1 is A
  (`main` at the freeze) against S (the candidate snapshot at maxAgents 0, maxVerifiers 0, budget
  line on); stage 2 is S against D (the same snapshot at maxAgents 8, maxVerifiers 2) with the
  matched arm M. The harness wrote a cap and the budget line only into the candidate and matched
  arms, so S could not be the baseline with the scope it had as the candidate.
- **Stage 2 runs one snapshot in both arms**, which the preflight refused as an operator mistake.
- **A v5 candidate would fail the preflight twice** (read from `core/subagents.ts`, not run): at
  maxAgents 0 and maxVerifiers 0 pired hides the launcher, so stage 1's candidate would fail the
  tool probe, which required it; and the delegation probe's scope named no cap, which a snapshot
  cut after ADR-029 reads as 0, so the probe's launches would be refused on every v6 grid.

### Decision

- **Any number of targets, at least one.** Ids key every cell, pin, pair and record, so a manifest
  that lists one id twice is refused.
- **The official corpora are pinned** in `eval/delegation-compare.pins.json` under `corpora`:
  - `v5-official`: the five ids, three passes and the manifest and truth hashes the runner
    hard-coded, moved unchanged. It is the only `kindless` corpus: a grid without `--grid-kind` is
    judged against it exactly as before, with the same reasons in the same words and order (tests).
  - `v6-fresh`: a placeholder with every field null, to be frozen with the pre-registration. It
    also pins the twins file's sha256.
  - `isOfficialGrid` and `compareMatchedRuns` take the official shapes; the runner passes the
    pinned one. The lib keeps the v5 constants as their default, and a test holds them equal to
    the pin.
- **Each arm's scope is configured, pinned and restored.**
  - `--baseline-max-agents <n>`, `--max-verifiers <arm>=<n>` (baseline, candidate) and
    `--budget-arms <arm,...>|none` (default `candidate,matched`, what every grid wrote) feed one
    function, `scopeFor`, which writes the keys in one order whatever the role. S's scope is then
    the same bytes as stage 1's candidate and as stage 2's baseline (test against the shipped
    kinds).
  - Unset, every arm writes what it wrote before, and the manifest gains no field (tests).
  - Each option is written into the manifest only when set, restored strictly by
    `optionsFromManifest`, and a changed one is a resume mismatch.
  - The matched arm states `maxVerifiers 0` beside `maxAgents 0` when the candidate states a
    verifier cap, so in stage 2 M's scope is S's. Without `--max-verifiers` it writes what it wrote.
  - One snapshot may run in both arms only when their scopes differ. The manifest then records
    `sameSnapshotInBothArms`.
  - `--subagents-arms <arm,...>|none` names the arms whose cells load the pinned pi-subagents
    (default candidate and matched). Stage 2 names the baseline too (see *Fairness*).
  - Without a grid kind, setting any of these makes the grid exploratory: the v5 official grid ran
    every arm at the configuration they leave alone.
- **Patched twins run beside the gate.**
  - `--twins <file>` reads the fresh corpus's `twins.json` exactly as written. A twin takes its own
    `name` as its grid id, names its target by id as `twinOf`, and keeps its advisory as a leak
    term, so the copy is stripped of files that name it (a fix commit is where a changelog names
    the advisory). Its answer key must be an empty list.
  - `--twin-arms <arm,...>` (default none) names the arms that run them; each needs the other. The
    arms are pinned in the manifest and the file by path and sha256 in its inputs; a change is a
    resume mismatch.
  - Twin pairs follow the gate pairs in each pass, in the twin arms only. They never enter
    `compareMatchedRuns` (a run it does not expect makes the grid incomplete), never bring the
    matched arm, and a twin's failure neither stops an official grid at once nor refuses its
    resume. They count toward progress and the breaker like any run.
  - `manifest.targets` carries a twin's `twinOf`, `fixed_regions` and `scope_loc`, and each run
    record its `twinOf`, which is what `eval/rescore.ts`'s control score reads. `summary.json`'s
    `twins` block lists, per arm, the runs, valid runs, claims and every cell. The gate's `stops`
    and delegation audit read gate runs only; the twins' stops are in their block.
  - The preflight grades a twin with a decoy claim, which must score 0 of 1, since there is no
    oracle; it probes the twin in its twin arms only, on a file its fix touched.
  - Twins on a corpus without them (the v5 one) are exploratory.
- **Named grid kinds.** `gridKinds` in the pins file fixes, per kind, fields that mirror the
  command line: the corpus; the baseline, as a git commit (checked file by file, as the v5 baseline
  was) or a snapshot digest (stage 2's S has no commit); the candidate digest; every arm option;
  the twin arms; the matched policy; retry; the breaker policy; the run limit.
  - `--grid-kind <name>` judges the grid against its kind, and against the kind's corpus and
    snapshots in place of the kindless pins. Each difference is an exploratory reason; an unknown
    kind fails the preflight. The kind is pinned in the manifest.
  - `v6-stage1` and `v6-stage2` are drafts of the pre-registration, every value to be frozen and
    both snapshots null. The two stages' command lines read as exactly their kinds (test).
- **The worst case counts N targets and the twins.** `gridWorstCaseMs` takes targets + twins pairs
  per pass, each no longer than the longest pair: a pool of workers taking pairs in order finishes
  a pair at least every longest-pair time while any is queued. Without twins it is the earlier
  formula (test).
- **The two probes can pass on a v5 candidate.** A candidate whose scope switches delegation off
  may show no launcher, as the matched arm may. The delegation probe's scope states maxAgents 8,
  the v3/v4 default, whatever the grid's cap: it proves the pinned pi-subagents path, not the arm.

### Fairness between arms

- **S is the same cell in both roles.** Whether an arm loads the pinned pi-subagents is a per-arm
  option (`--subagents-arms`, default candidate and matched, as before), pinned like the others,
  and `v6-stage2` names the baseline, so S loads it as stage 2's baseline exactly as it did as
  stage 1's candidate. One function, `cellModelInputs`, gives everything the harness writes or
  passes per arm that could reach the model (snapshot, scope bytes, pi's settings, the pi-subagents
  config, the extension list, prompt, model, effort, retry policy), and `prepareCell` writes
  exactly those; a test holds S's equal in both roles, and D's equal to S's but for the caps.
  A baseline that loads pi-subagents with delegation off is checked as the matched arm is: the
  launcher is allowed, not required, and a worker it launched fails the run.
- **Twins share the provider window with the gate.** In stage 1 they double each pass's runs
  (twelve twin pairs of two arms beside twelve gate pairs), and they run after the gate pairs of
  their pass, so a grid stopped part-way has spent its passes on the gate first.

### Consequences

- The new module `eval/delegation-compare-grid.ts` is in `HARNESS_FILES`, and `harnessSha256`
  changes, so a v5 grid resumes from a worktree at its own commit, as for any harness edit.
- **Freezing edits the pins file.** Filling `v6-fresh` and the two kinds changes the harness pin,
  so the freeze comes before the first grid, as for a candidate.
- **The v6 grids' worst case is far past the OAuth cap** (computed, not measured). Stage 1 at 12
  targets and 12 twins, 6 passes, concurrency 2 and 4 h per arm: 576 h fail-fast, and 2,311 h
  with the default breaker. The check then sizes the 168 h cap and records it as capped, as it does
  for any grid past it, and a codex token lives 240 h. The operator states
  `--auth-horizon-hours` and refreshes between resumes, or the grids are split.
- **`approvedForThisModel` is still ADR-026's rule.** On a kind grid, "official" means the grid ran
  as its pinned kind; the pre-registration's decision rule is computed from the runs by
  `eval/rescore.ts` and `eval/paired.ts`, and `summary.json` says so.
- **Readers see a twin under its name.** `eval/rescore.ts` keys `manifest.targets` and run
  records by id, so it finds a twin's fixed regions under its name. A reader that pairs rows by
  target and pass pairs a twin's two arms with each other, never with its target.
- **The corpus directory holds the twins too**: `<name>.pristine` and the corpus-side
  `<name>.truth.json` for each, as for a target.

### Rejected

- **Hard-coding the v6 ids beside the v5 ones.** Every freeze would be a code edit, and the pins
  file is where freezes already land.
- **Twins in the corpus manifest with a `twinOf` field.** The fresh corpus writes them to their own
  file, whose twins share their target's id. Re-keying at load keeps that file byte-identical to
  what the corpus build wrote, so its hash is pinned as it is.
- **An advisory-shaped twin id** (such as the advisory with a suffix). It is what the leak check
  hunts for in anything a cell sees; a twin's name is already a redaction term.
- **Twins in the gate.** A twin has no labels, so it adds claims and no true positives, and its
  count would move precision for a reason that is not the arms' ability to find the advisory.
- **An official v6 grid without a kind**, recognised by its corpus alone. The arm options would
  then be unpinned, and stage 1 and stage 2 share one corpus.
- **The budget line always in the baseline's scope.** Every v5 baseline scope would change.
- **Refusing any grid whose worst case passes the OAuth cap.** It would refuse option sets that ran
  before (a v5 grid at more passes) that the check has always capped and recorded.
