# 09 · What pired missed, and why

*August 2026*

A recall number says how many were missed. It does not say what kind of thing
gets missed, and that is the only part that tells you what to change. This is the
per-bug analysis of every miss recorded so far: six of eight truth entries on the
sealed library corpus, and the single scored target on the application corpus.

## Method

A miss is a truth entry — a location the maintainer's own fix touched — that no
reported finding matched. For each one this records three things: what the bug
was, what the ledger shows the harness did, and what it reported instead. The
third matters most. A blank is a different failure from a wrong answer, and both
are different from a right answer in the wrong place.

### The correlation that matters

Two of six targets recorded hypotheses. Those two are the only two that found
anything.

```
engaged (hyp > 0)    2 targets   →  2 found something
idle    (hyp = 0)    4 targets   →  0 found anything
```

This corrects an earlier reading of these runs as uniformly idle. They were not:
the mechanism fired on jinja2-ftwwg0 (117 hypotheses) and sqlparse-fty7y9 (92),
and both scored. Where it did not fire, the target scored zero every time. The
harness is not a weak reviewer on these targets — on four of six it did not
review at all, and the recall number folded that in silently. That is precisely
what the new MECHANISM IDLE reporting exists to stop.

## Three failure classes

**A · Silent (4 targets, 5 missed entries).** No hypotheses, nothing reported.
`requests-ftwzep` recorded eight surface elements and then stopped; the other
three recorded almost nothing. Whatever these runs were, they were not reviews,
and their zeros are not evidence about detection.

**B · Right class, wrong location (PYSEC-2026-3698).** The key names three files
for one ReDoS. pired reported *"Quadratic ReDoS in SerializerUnicode SPLIT_REGEX
— unbounded CPU via sqlparse.format()"* at `utils.py:21`, matching the `utils.py`
entry and missing `keywords.py` and `lexer.py`. It had the right vulnerability,
the right mechanism, and one of the three sites. Scored 1/3, which understates
what it understood.

**C · A different, plausible bug (jinja2, sqlparse).** An RCE claim in jinja2's
template compiler and a code-injection claim in sqlparse's output formatter.
Neither has been verified. Neither is in the advisory, so both score as false
positives, but the key only knows about the one bug the CVE was filed for.
Precision against a patch-derived key is a lower bound, and these are the entries
that make it one.

## The application corpus: flarum

`GHSA-xjvc-pw2r-6878` — path traversal in the LESS parser via theme colour
settings, `framework/core/src/Forum/ValidateCustomLess.php:46`, an incomplete fix
for CVE-2023-27577.

This is the most diagnostic miss of the set, because nothing failed:

```
inventory     10 endpoints, no shoehorning
hypotheses    174 — 168 refuted, 6 confirmed, all settled
findings      3 outside the advisory, unverified
recall        0/1
```

The agent reviewed properly and reported three problems outside the advisory,
none of them verified. It also tested path traversal, the exact class of the
bug, against `/forum/gdpr/export/{file}` and refuted it.

**Zero of its 174 hypotheses mention the LESS parser or `ValidateCustomLess`.**
The file was inside the scope it was given. It never entered the hypothesis space
at all.

## What the misses have in common

Setting aside the silent runs, every missed bug shares a property:

| bug | where it lives |
|---|---|
| `.netrc` leak on redirect | state carried *between* requests |
| `verify=False` stickiness | object lifecycle across a `Session` |
| sandbox breakout via `attr` filter | indirect reference, one hop from any sink |
| `TokenList.__init__` O(subtree) | algorithmic complexity in a constructor |
| ReDoS in `keywords`/`lexer` regexes | algorithmic complexity in a table |
| flarum LESS traversal | a settings validator behind a compile step |

**None is a sink reachable in one hop from an entry point.** pired's coverage
matrix is `checklist classes × recorded surface elements`, and its surface
vocabulary is `host / service / endpoint / param / tech`. Every one of these bugs
lives somewhere that matrix has no cell for: in state that persists across calls,
in an indirect reference, in the complexity of an algorithm, or behind a
pipeline stage.

The application corpus fixed the *first* half of the problem — pired can now
enumerate a real request surface, which it could not do on a library. The flarum
miss says the second half is untouched: **enumerating the surface does not reach
what sits behind it.**

That is a hypothesis from one scored application target, not a conclusion. The
manifest tags ten targets `direct` (the fix touches a route, controller,
middleware or serializer) and ten `indirect`. If pired scores on `direct` and
near-zero on `indirect`, this is confirmed and the fix is a coverage model with
kinds beyond the request boundary — `sink`, `validator`, `job`, `trust-boundary`.
If it misses both, the problem is detection, not coverage.

## A caveat on the key

The one clean library find matched truth entry `sandbox.py:10` whose
`line_range` is `[10, 390]` — the fix touched hunks across 380 lines, and
`refineKey` collapses them to one entry per file. A finding at `sandbox.py:388`
matches. That is file-level attribution wearing a line number.

It is the documented intent — *"one claim per file, around here"* — but it means
`found 1/1` on that target asserts the right file, not the right line. Read every
number in this document with that resolution in mind.
