# Real-app corpus, August 2026

*First measurement against real vulnerabilities in real software. Recall roughly
halves versus the teaching app, and the two harnesses find different bugs.*

## Why this exists

Every number in `research/01`–`06` is measured against DVBank: a deliberately
vulnerable teaching app with 53 labelled bugs and a published answer key. Bugs
placed to be found, in code written to contain them.

`04 §7` and the README both note that one target is not a capability claim. This
is the corpus that tests the claim that matters for a consultant — **can the
harness find a real vulnerability in real software it has never seen?**

## Method

17 targets built from OSV advisories with maintainer fix commits. For each, the
repository is checked out at the commit **immediately before** the security
patch, and the patch itself is the answer key: file plus line range of the
vulnerable construct. Leak files (advisories, changelogs, security docs) are
stripped, and a target whose key does not resolve to a real file is rejected at
build time.

```
sqlparse ×2 · requests ×2 · jinja ×2 · quart · werkzeug · flask ×2
tornado ×2 · aiohttp · gradio ×2 · mlflow ×2
17 targets · 23 ground-truth entries
```

These are **1-days, not 0-days**: real, recently-fixed vulnerabilities, chosen
post-cutoff so the fix is unlikely to be memorised. That is the same ground-truth
design SWE-bench uses, and it is as close to discovery as an answer key permits.

Both arms: same grader, same per-target key, `window=3`. pired ran
`qwen/qwen3.8-27b` pinned to one host through a metering proxy; codex ran its own
frontier model on a subscription.

## Results

Three single-pass measurements, two of them the same harness on the same targets:

| run | pooled recall |
|---|:--:|
| pired, run 1 | 7/23 = **0.304** |
| pired, run 2 *(same harness, same targets, all scoring fixes)* | 5/20 = **0.250** |
| codex | 6/23 = **0.261** |

**The two pired runs differ by more than pired differs from codex.** Any ranking
read from these numbers is reading noise.

### Reproducibility is 38%

Per target, across the two pired runs:

```
hit in both      1377 (flask) · 1873 (requests) · 2044 (werkzeug)
run 1 only       1409 (gradio, 2/2) · 1475 (jinja) · 3699 (sqlparse)
run 2 only       1872 (requests) · 3546 (aiohttp)
```

Only **3 of 8** ever-hit targets were hit in both runs. A single pass finds
roughly five to seven of the twenty-odd truth entries, but *which* five to seven
is close to a coin flip per target.

**So the headline this document originally carried — pired 0.333 against codex
0.286, "a local 27B edges a frontier agent" — is not supported.** That was a
one-finding lead measured once, and run-to-run variance is ±2 findings. The
defensible statement is that **pired and codex are indistinguishable on this
corpus at n=1**, both landing between 0.25 and 0.33.

That reading was itself too generous to the instrument, and §3a corrects it: run
three passes of *codex* over the same targets and it reproduces. The corpus is
not the noisy component. pired is.

## 1. Recall halves on real targets

| | pired | codex |
|---|:--:|:--:|
| DVBank (teaching app, published key) | 0.74 | 0.68 |
| Real CVEs in real software | 0.33 | 0.29 |

**This is the most useful number in the project.** Any capability claim built on
the DVBank figure overstates real-world performance by roughly **2×**, for both
harnesses equally. It is not a pired weakness; it is what a labelled teaching app
measures versus what real code does.

## 3a. The variance is pired's, not the corpus's

Six targets, three passes each, both harnesses, 36 runs. Every pass starts from a
wiped engagement workspace (`rm -rf` before each target) and a fresh process; no
run resumes a prior session, and the target trees are unmodified between passes.

```
                pired 1 2 3     codex 1 2 3
requests 1873     x x x           x x x
requests 1872     . x x           x x x
jinja    1471     x . .           x x x
jinja    1475     x x x           . . .
sqlparse 3699     x . .           x . .
sqlparse 3698     0 1/3 2/3       1/3 1/3 1/3

same answer all three passes:   pired 3/6      codex 5/6
```

**codex reproduces; pired does not.** codex returned an identical result on five
of six targets, including finding exactly one of the three bugs in
`sqlparse-3698` three times running. pired changed its answer on three of six and
drifted 0 -> 1 -> 2 entries on 3698.

This kills the convenient explanation. The instrument is stable enough to
measure a harness; the earlier conclusion that "the corpus cannot rank anything"
was wrong in pired's favour. What it cannot do is rank two harnesses whose
difference is smaller than *pired's own* run-to-run spread — and that spread is a
property of the harness, not the benchmark.

### Each harness has a reproducible blind spot

Two rows are the most useful result in this document:

| target | pired | codex |
|---|:--:|:--:|
| `jinja-1475` sandbox breakout via indirect reference | **3/3** | **0/3** |
| `jinja-1471` sandbox breakout via attr filter | 1/3 | **3/3** |

Perfect reproducibility in opposite directions on two vulnerabilities in the same
package. Neither is variance: each harness finds one every time and misses the
other consistently. That is a genuine capability difference, and it is the
strongest evidence in this project that the two tools are complements rather than
substitutes — a claim §2 could only gesture at, because a single pass cannot
separate complementarity from noise.

### What it means for pired

Reproducibility is not a nice-to-have for an engagement tool. A consultant signs
a report; a finding that appears in two runs of three is one a reviewer cannot
rely on and an operator cannot defend. pired's depth is real — it runs four to
ten times longer per target than codex and catches bugs codex never sees — but
the consistency gap is now a measured defect with a number attached, and it
belongs on the roadmap ahead of any further recall tuning.

## 1b. The agent was retrieving the answer, not only finding it

Every number above was measured with the network open. Reading the session
transcripts afterwards showed what the agent actually did with it:

```
retrieval attempts per target   (pip download · git clone · diff -ru · api.osv.dev · pypi.org)
  jinja2-ftwwfw     34      flask-ftxh5m      17      aiohttp-fty737   17
  gradio-ftwwap     13      flask-1377        12      aiohttp-3546     11
```

One transcript runs the method end to end: diff the tree against jinja 3.1.5,
spot the fix that is missing, build a proof of concept, `RCE CONFIRMED`. The
corpus is built from *pre-patch* commits, so the released version **is** the
answer key. `fetch.ts` strips `.git`, changelogs and advisories from the target;
none of that matters when the fix is one `pip download` away.

**This invalidates the design of any 1-day benchmark against public CVEs for a
network-capable agent**, not just this one. It is the most portable finding in
this document.

### The sealed re-run

Both holes closed: targets restored from an immutable snapshot before every run
(the agent writes PoCs and scanner output into the tree it is reviewing, so pass
2 reviewed a different codebase than pass 1), and the network denied through
pired's own scope gate — `mode: enforce`, `authorized: true`, zero permitted
hosts. Verified against a live probe: the agent refused a deliberate `curl` to
`api.github.com` on its own reasoning. Zero upstream clones across the whole run.

| target | sealed | open |
|---|:--:|:--:|
| `jinja-1475` | **1.00** *(1027s)* | hit |
| `sqlparse-3698` | **0.33** *(950s)* | 0 → 1/3 → 2/3 |
| `jinja-1471` | 0.00 *(153s)* | 1/3 |
| `sqlparse-3699` | 0.00 *(194s)* | 1/3 |
| `requests-1872` | 0.00 *(156s)* | 2/3 |
| `requests-1873` | 0.00 *(139s)* | 3/3 |
| **pooled** | **2/8 = 0.250** | 0.250 – 0.304 |

**Recall barely moved. Effort did.** The two sealed hits took 950 and 1027
seconds of sustained analysis; the four misses gave up after ~150 seconds of
scanner sweep. With the network open the agent had a third, much cheaper route to
the same score.

So the honest reading is neither "the numbers were fake" nor "retrieval did not
matter". The agent has two modes — reason from source, or fetch and verify — and
they reach comparable recall at very different cost. Which mode it picks depends
on what the environment offers, and that is a large part of why passes disagreed.

`jinja-1475` is the result worth keeping: **full recall, sealed, on a
vulnerability codex missed three times out of three**, earned by reading the
source.

### What this costs the reproducibility comparison

§3a measured pired at 3/6 stable against codex at 5/6 **on contaminated trees**,
with both arms free to retrieve. That comparison is not void — both arms ran under
the same conditions — but it measured consistency of a mixed retrieve-or-reason
strategy, not of analysis. A sealed reproducibility run has not been done.

## 2. Coverage comes from repetition and diversity, not from picking a winner

Pooling every pass — pired run 1, pired run 2, codex — reaches **10 of 17
targets**, against 5–6 for any single run.

```
found by at least one pass
  1377 flask · 1409 gradio · 1471 jinja · 1475 jinja · 1872 requests
  1873 requests · 2044 werkzeug · 2151 flask · 3546 aiohttp · 3699 sqlparse
```

Two effects are tangled here and this design cannot separate them: different
harnesses find different bugs, *and* the same harness finds different bugs on a
second pass. Both point the same way for an operator — **more passes and more
than one tool beats optimising which single tool to run** — but the earlier
claim that the harnesses are specifically complementary is only half the story.
Much of that apparent complementarity is simply variance.

## 3. Three limits, all understating pired

**Extraction floor.** pired recorded 3.2 findings per target but only 2.1 carried
a line the grader could place — 20 findings across the corpus are unscoreable
however correct. `fromLedger` now resolves a finding's file through the inventory
element it targets, but still requires a line stated in the finding itself;
inventing one would let a file-only finding drift into a truth window and inflate
recall, which is the worse error.

**Subagent delegation was broken for the whole run**, and the root cause turned
out to be pired's. `pi-subagents` spawns async children with extension bindings
deliberately stripped (`omitExtensionBindingsEnv`), so a child never loads pired
and never sees a provider pired registered through `registerProvider`. The child
cannot resolve its model, reports `0 turns | 0 tokens | 0 tools`, and a parent
that pired's own prompt told to delegate and then block on the fleet waits on it
forever — a silent deadlock at ~0% CPU that only an external timeout ends.

Both mlflow targets died this way, twice each. It reproduces on any target large
enough that the agent chooses to delegate, which means **the harness failed
exactly where its own advice was most correct**.

Fixed: `mirrorProvidersToPi()` writes the same providers into pi's native
`~/.pi/agent/models.json`, which every pi process reads, extension or not. The
failing case — an extension-less process resolving
`openrouter/qwen/qwen3.8-27b:low` — now succeeds. Merged by provider id, so a
user's own entries are untouched.

The corpus numbers above were measured *before* this fix, with delegation
unavailable throughout. codex has no subagent capability either, so the
head-to-head comparison is unaffected; pired's absolute figure is the one that
may rise on a re-run.

**Two mlflow targets timed out** at 30 minutes, wedged behind the same subagent
failure, and are excluded from the common-15 figure. Excluding them *raises*
codex's score (0.261 → 0.286), since codex scored zero on both, so the exclusion
does not flatter pired.

pired's figures are therefore **lower bounds**, and noisy ones.

## 4. Where both harnesses failed

Nine of seventeen targets produced nothing from either arm: tornado ×2, quart,
aiohttp, mlflow ×2, gradio-1410, jinja-1471 (pired), sqlparse-3698. The pattern
is size — the targets where both fail are the large ones, and sqlparse-3698's key
has 3 entries in a hardened tree. Neither harness reviews a 300-file package
deeply enough in one pass; the limiting factor is review depth, not reasoning.

## 5. Two measurement bugs found and fixed

**The grader scored correct findings as misses.** Corpus truth from OSV carries a
file and line range but no CWE. `class_matches()` permits a location-only match
only when the finding omits both class fields, so a finding reporting a CWE —
exactly what both harnesses are prompted to produce — fell through to equality
checks against a truth class that does not exist, and was scored a miss. Every
corpus zero in the first run, both arms, was this. Scoring now strips class
fields when the truth is classless; DVBank's own key carries classes and is
untouched.

**A stray `AGENTS.md` contaminated the DVBank target.** 13 KB of pired's own
system prompt, written into `eval/variants/clean/` by a harness run on 25 August
and never removed. Both pi and codex read `AGENTS.md` as instructions, so it
silently handed pired's full methodology, including the 19-class weakness floor,
to any agent reviewing that tree. A codex run against it returned **0 findings**;
the same scan with the file removed returned **28**. Quarantined. Any result
measured against `clean/` after 25 August should be re-checked for it — including
the "vanilla pi" arm, whose vanilla-ness it would have undermined.

## 6. What this corpus can and cannot measure

**Can measure.** That real-CVE recall is roughly half the teaching-app figure —
a 2x gap, consistent across both harnesses and all three passes, far larger than
the noise. That is the calibration this corpus was built for and it holds.

**Cannot measure.** Which harness is better *on recall*. Three points of pooled
recall is one finding, and one pired pass moves by two. Ranking on recall needs
n>=3 per target across all 17, which is a different and more expensive
experiment.

**Can measure, and did.** Reproducibility. Three passes over six targets was
enough to separate the harnesses decisively on consistency (5/6 vs 3/6) and to
establish two reproducible blind spots. That turned out to be the more useful
axis, and the cheaper one.

**A rule for anything built on this corpus in future:** never report a single-pass
pooled recall as a comparison. Report the interval across repeats, or report
nothing.

## 7. Threats to validity

- 23 truth entries across 17 targets, 1–4 per target. A single finding moves
  pooled recall by ~4 points; this ranks harnesses coarsely at best.
- Ground truth is the maintainer's patch location. A harness that finds a
  *different* real bug scores zero — precision here is a lower bound on value,
  and several unscored findings may be genuine.
- **One pass per target is the dominant limitation.** Two pired runs over the
  same targets agreed on only 3 of 8 ever-hit targets. Everything comparative
  here is inside that noise.
- One model per arm, one provider.
- codex ran with delegation available and pired did not; the arms are not equal
  in capability, and the inequality runs against pired.

## Correction (2026-09-23)

§3 above explains the broken-delegation incident with a mechanism that later reading of the
package showed to be wrong. `omitExtensionBindingsEnv` does not strip a child's extension
bindings: it deletes one env var (`PI_SUBAGENT_EXTENSION_BINDINGS`, a metadata blob), and only
in pi-subagents' out-of-process runners. A foreground child is an in-process pi session and loads
whatever extensions its agent lists. The full analysis is in
[ADR-027](../docs/decisions.md).

What was **measured** here still stands, and is left unchanged: subagent delegation was
unavailable for the whole run, both mlflow targets timed out at 30 minutes wedged behind it, the
child reported `0 turns | 0 tokens | 0 tools`, and `mirrorProvidersToPi()` fixed the failing case
(an out-of-process child that could not resolve its model). Only the *why* was misstated — the
child could not resolve its model, not "could not load pired" — and it does not move any number in
this report.

Loading pired and resolving pired's providers are separate questions. Before pi-subagents 0.68, an
in-process foreground child also knew only pi's own providers, so the mirror is what let it
resolve one pired registered. From 0.68 such a child inherits the parent's providers (pi-subagents
CHANGELOG 0.68.0).
