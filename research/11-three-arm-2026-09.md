# 11 · Three arms on the application corpus

*September 2026 — pired, bare pi and codex on the same five targets*

## The question

`research/10` left the corpus scoring zero and could not say why. Every arm ran
one harness against one model, so a zero was equally consistent with "the harness
does nothing", "the model cannot review", and "the benchmark is unwinnable". This
pass separates them: two harnesses over the **same model**, and a third agent
entirely, on the same targets, keys, grader and seal.

| arm | harness | model |
|---|---|---|
| 1 | stock `pi`, no pired extension loaded | deepseek-v4-flash-0731 |
| 2 | **pired** | deepseek-v4-flash-0731 |
| 3 | codex | gpt-5.6-sol |

Five targets, one per project, chosen as the first of the round-robin manifest:
filebrowser (Go), LinkAce (PHP), fat_free_crm (Ruby), whoogle-search (Python),

## What the averages say, and what a single pass said

A single pass said pired 7/24, codex 4/24, bare pi 2/24, and that is the number
this document reported in its first version. Three passes say pired 3.0, bare pi
3.3, codex 4.0. **The ordering reverses.** The 7 was the top of pired's range and
was read as a result.

Three things survive averaging:

- **codex is the most consistent by a distance** — 4, 4, 4, no variance at all,
  against pired's 2–4 swing on identical inputs.
- **pired's precision is the worst of the three**, 0.065 against bare pi's 0.192.
  It grades 139 findings to bare pi's 52 for one fewer true positive. Whatever
  the ledger is adding, it is not selectivity.
- **The harness does not separate from the model.** pired and bare pi run the
  same model on the same targets and differ by 0.3 entries out of 24 — inside
  the run-to-run spread of either. The earlier claim that pired found 2.5x what
  bare pi found came from comparing one pass of each.

Across all six pired passes recorded in this session — including three on earlier
commits — the totals are 5, 7, 3, 2, 4, 3: mean 4.0, range 2 to 7. A corpus where
one arm's spread is 2 to 7 out of 24 cannot resolve a difference of 1.

**fat_free_crm was never solved by any arm in any pass** — 0 for 9. Its two truth
entries are `app/models/polymorphic/task.rb:191` and
`lib/fat_free_crm/version.rb:12`; a version constant is not something a review
finds by reviewing.

## Why the other 17 were missed

Every miss was classified from the ledger and the transcript together. Two facts
hold across all of them, and both overturn `research/10`:

- **The file was opened in 17 of 17.** The agent read every file containing a
  missed entry. "It never looked" was true of qwen and is not true here.
- **The file was recorded as surface in 0 of 17.** Surface is recorded as routes;
  findings and truth live in files. Since coverage is `classes x surface`, the
  matrix cannot point at a file it has never held.

| cause | n |
|---|---:|
| finding in the right file, location the grader cannot read | 8 |
| finding in the right file, wrong line | 6 |
| file opened, nothing recorded | 2 |
| class confirmed, no finding promoted | 1 |

The six wrong-line cases split further: four are **4–12 lines** from the truth
(the grader's window is 3), and two are 49 and 101 lines away — those are a
different bug in the same file, not a location error.

The single confirmed-but-unpromoted case is `runner/runner.go:63` carrying
`cmdi:confirmed` with no finding at that line: the hypothesis ledger and the
findings ledger disagreeing about what the engagement knows.

## One bug found, and one fix that did not earn its keep

`http/share.go:84` was recorded **exactly** on truth entry GO-2026-5096-1 and
then overwritten seconds later by `http/public.go:58` — one finding id, three
sinks, last write wins. `mergeRecord` now accumulates locations for findings and
`fromLedger` grades against all of them.

It has not been exercised since. Across two full passes over five targets, **no
finding was ever again recorded at differing locations under one id**, so the
field never appeared. The entry it was built for is a hit in the re-run anyway,
because nothing overwrote it that time. The bug is real and the evidence for it
is in the first run's ledger; its frequency is one occurrence in ten target-runs.

A second change was tried and **withdrawn on measurement**: grading against every
file path named anywhere in a finding's prose. It took 48 graded findings to 93,
landed none of them in a truth window, and halved precision from 0.104 to 0.054.
A file mentioned while explaining a bug is context, not a claim about where the
bug is.

## Why one pass is not a measurement here

The same five targets, same model, same prompt, run twice, differed like this:

| target | hypotheses, pass 1 | pass 2 |
|---|---:|---:|
| LinkAce | 81 | 379 |
| fat_free_crm | 61 | 210 |
| whoogle-search | 15 | 166 |

Recall moved 5/24 to 7/24 between those two with no change that accounts for it,
and a later pass on the same code scored 3/24. Every single-pass number in the
first version of this document — including all of the ones that favoured pired —
was inside that noise.

The rule this corpus earns: **three passes minimum, report the range, and treat a
gap smaller than the spread as no gap.**

## The scribe, measured

The scribe — the pass that re-reads the review and extracts records from it — is
opt-in since it moved off `turn_end`, and a headless run had no way to enable it:
across the three passes above it fired **zero times**. Earlier passes in this same
session, on commits where it defaulted on, fired it four to eight times per
target, so the session's numbers were comparing two configurations. `PIRED_SCRIBE=on`
now exists for exactly this reason.

Three passes with it on, against the three above, same commit lineage, same model,
same targets, same grading:

| | scribe off | scribe on |
|---|---|---|
| passes | 5, 2, 3 | 2, 3, 4 |
| mean | **3.3** | 3.0 |
| union | **9/24** | 5/24 |
| ledger findings | 151 | 149 |
| hypotheses | 3,685 | **3,887** |
| precision | **0.049** | 0.039 |
| wall clock per pass | **~11 min** | ~28 min |

The means overlap — 3.3 against 3.0 with ranges of 2–5 and 2–4 — so on recall the
honest answer is no measurable difference. Union is lower with it on, and union
over three passes is a noisy statistic, but 9 against 5 is not a direction that
supports switching it on.

What is not ambiguous is the cost: **2.5x the wall clock**, from roughly thirteen
extra model calls per target each carrying the review buffer. And what it buys is
visible in the one number that moves in its favour: **202 more hypotheses**. That
is the class roll-call doing its job — filling in cells the agent never works
through systematically — which is coverage, not findings. A patch-derived key does
not measure it.

The mechanism explains itself. The scribe was built to rescue a model that would
not record: qwen3.8-27b made **3 `record` calls across five sessions** and the
extractor produced every hypothesis and finding. deepseek makes **70 on a single
target**. There is nothing left to rescue, and re-reading a growing buffer to
re-emit what the agent already wrote costs a model call each time.

**On this corpus, with a model that records for itself, the scribe is not worth
its time.** Opt-in is the right default. Its value should be argued on coverage
completeness, and measured against something other than a maintainer's patch.

## Open

- **Surface and findings do not share a vocabulary.** Routes in the matrix, files
  in the findings, files in the key. Until they meet, coverage cannot direct a
  review toward an untested file, which is what 8 of 17 misses needed.
- **A confirmed class should not be able to leave a file unreported.**
- **Line granularity.** Four misses sit within 12 lines of their truth. The
  function-level axis built in `research/10` covers this and should be reported
  beside line-window recall rather than instead of it.
